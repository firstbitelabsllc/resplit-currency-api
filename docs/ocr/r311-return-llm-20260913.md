## Observed failure and bounded change

The September 13 attested physical-device scan returned an Azure partial after
10,355 ms. Production Loki joined the same request to LLM success 1,789 ms
after the response log. The saved receipt retained 13 rows, 18 units and three
unknown amounts, against the independent 10-group/15-unit oracle. Correct total
agreement and LLM success do not themselves prove correct LLM itemization.

Set the already-supported `LLM_SCAN_AZURE_GRACE_MS` to `"0"` in root and named
production Wrangler variables. The existing router then waits for the terminal
LLM result and returns it in the same `/ocr/analyze` or `/ocr/dual-scan` response.
There is no router-code, model, prompt, image-size, provider, authentication,
accounting, cache, client-protocol, or migration change. Terminal provider failure
still returns the available Azure partial. Already-started provider work remains
chargeable exactly once.

Tradeoff: the existing LLM transport can take up to its 60-second timeout when
the provider stalls. The current iOS `RemoteScanProvider` request timeout is
90 seconds. This change is not evidence of the older 15-second visible-wait
goal or the seven-day latency targets; those claims need their own current proof.
